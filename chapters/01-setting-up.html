1  Setting Up Your Environment

Draft|Code: script · exercises · solutions · all chapters|To comment, select a passage and annotate it; see how reviews work.

What has to be installed, and in what shape must a return series arrive, before any portfolio in this book can be computed? The second question has two canonical answers that do not agree: Wickham (2014) defined a tidy table as one observation per row and one variable per column, and Zeileis and Grothendieck (2005) built the ordered, date-indexed matrix that zoo and xts carry and that every optimization function in PortfolioAnalytics expects. Both are used in every chapter of this book, and the boundary between them is crossed each time data are prepared for an optimizer or read back out of one, so we fix it here, once.

We first list what to install and what each package is for, then set out the two data models and why neither can be given up, then cross the boundary between them on the book’s own data and break it in the three ways it breaks, and finally read the data once in the way every later chapter will. On the horizon axis that Section 3.1 defines, this chapter is neither strategic nor tactical: it allocates nothing.

Three programs come first: R, of which the book was built on 4.6.1 and anything from 4.4 onward will do; an editor, RStudio or Visual Studio Code with the R extension; and Quarto (Allaire et al. 2022), needed only to render the book’s source, not to run its code. The packages install from CRAN in one call.

install.packages(c(
  "tidyverse", "xts", "zoo",                                  # data models
  "PortfolioAnalytics", "PerformanceAnalytics",               # the subject
  "ROI", "ROI.plugin.quadprog", "ROI.plugin.glpk", "quadprog", # convex solvers
  "osqp", "CVXR", "DEoptim", "GenSA", "pso",                  # more solvers
  "corpcor", "renv"                                           # shrinkage, pinning
))

The companion package tidypm is not on CRAN. It holds the modeled market of Section 2.2, the two coercion functions this chapter is about, and the machinery that PortfolioAnalytics does not cover, recorded in Appendix D; it installs from GitHub.

pak::pak("sstoeckl/tidypm")

renv.lock records every version the book was built against, and renv (Ushey and Wickham 2026) restores that record, so that the printed numbers reproduce to the last digit rather than to whatever CRAN offers on the day.

renv::restore()

The tidyverse (Wickham et al. 2019) is the data-manipulation half of Table 1.1, with Wickham et al. (2023) as its reference; xts (Ryan and Ulrich 2026) on top of zoo (Zeileis and Grothendieck 2005) is the time-series half. PortfolioAnalytics (Peterson and Carl 2026b) and PerformanceAnalytics (Peterson and Carl 2026a) are the subject and its engine. The solvers are backends that PortfolioAnalytics dispatches to by name: ROI (Theußl et al. 2020) for quadratic and linear programs, CVXR (Fu et al. 2020) for convex problems ROI cannot express, and DEoptim (Ardia et al. 2011), GenSA and pso for problems that are not convex at all. Section 13.1 says which to use when, and Appendix C tables which constraint each supports.

14 of the 115 exports carry a _v1 or _v2 suffix. They are the interface of an earlier generation of the package, kept so that old scripts keep running, and they are why an answer copied from an old forum post fails against the current release. The unsuffixed add.objective(), add.constraint() and optimize.portfolio() are the package; this book uses only those.

The other absence is data. Of the 115 exports, none fetch anything, and the package bundles 1 dataset, indexes. It optimizes what it is handed, and handing it the right object is the subject of this chapter.

1.1 Two Data Models

A return panel is a set of numbers indexed by a date and an asset, and there are two ways to lay it out, each of which makes some operations natural and others awkward.

The tidy layout of Wickham (2014) stores one observation per row: a date, an asset identifier and a return. A panel of \(N\) assets over \(T\) periods is a table of \(TN\) rows and three columns, and every operation of relational algebra applies to it directly: a sub-period is a filter on the date, a universe is a filter on the asset, a currency return or a yield is a join on the keys, and a computation that runs asset by asset is a grouped mutate. That is how the real data sleeves of Section 2.3 are assembled, how the screens of Section 20.2 are applied, and how every figure in the book is prepared, since ggplot2 consumes long data and nothing else.

The wide layout stores the same panel as a \(T \times N\) matrix with the dates as an ordered index and the assets as named columns. In the notation that Section 2.1 fixes,

\[ \boldsymbol{R} = \begin{pmatrix} r_{1,1} & \cdots & r_{1,N} \\ \vdots & & \vdots \\ r_{T,1} & \cdots & r_{T,N} \end{pmatrix}, \qquad \boldsymbol{r}_t' = (r_{t,1}, \dots, r_{t,N}), \tag{1.1}\]

where \(\boldsymbol{r}_t\) is row \(t\), the cross-section of returns on date \(t\). A portfolio with weight vector \(\boldsymbol{w}\) earns

\[ r_{p,t} = \boldsymbol{r}_t'\boldsymbol{w} = \sum_{i=1}^{N} w_i\, r_{t,i}, \tag{1.2}\]

and the sample moments that Section 9.1 optimizes over are matrix expressions in \(\boldsymbol{R}\) and the vector of ones \(\boldsymbol{\iota}\):

\[ \hat{\boldsymbol{\mu}} = \frac{1}{T}\,\boldsymbol{R}'\boldsymbol{\iota}, \qquad \hat{\boldsymbol{\Sigma}} = \frac{1}{T-1} \left(\boldsymbol{R} - \boldsymbol{\iota}\hat{\boldsymbol{\mu}}'\right)' \left(\boldsymbol{R} - \boldsymbol{\iota}\hat{\boldsymbol{\mu}}'\right). \tag{1.3}\]

zoo (Zeileis and Grothendieck 2005) made this layout a first-class object in R by attaching an ordered index to a matrix, and xts (Ryan and Ulrich 2026) specialized it to time, so that subsetting by date range, aligning two series, changing the frequency and rolling a window are each one call. Every function in PortfolioAnalytics and PerformanceAnalytics takes this object and nothing else; there is no method for a data frame.

Neither layout can be dropped: the long table is where data are built, because joining, filtering and grouping are relational operations and a matrix has no join, and the wide matrix is where portfolios are computed, because 1 through Equation 1.3 are matrix expressions. The boundary is therefore crossed in a fixed direction, long to wide once after the panel is built, wide to long whenever a result is to be drawn. timetk and tsibble hide the crossing; the book does not use them, because an explicit crossing can be checked.

The three equations also say what can go wrong, before any code does. In 1, \(T\) is one number shared by every column, so a panel in which one asset is missing a date has no matrix representation until the gap is filled or the date is dropped, and either choice changes Equation 1.3. In Equation 1.2, the \(i\) that indexes \(w_i\) and the \(i\) that indexes \(r_{t,i}\) must be the same asset, which a matrix product enforces by position and nothing else. And the map from \((t, i)\) to \(r_{t,i}\) must be a function: a panel in which some \((t, i)\) appears twice describes no matrix at all. These are the three failure modes of the boundary, and Section 1.2 produces each from the book’s data.

1.2 The Tibble–xts Boundary

tidypm provides the crossing in both directions. as_xts_pm() takes a long table and the names of its date, identifier and value columns and returns the matrix of 1; as_pm() takes the matrix back to three columns. The book’s data ship in the long form.

1.2.1 Three ways the boundary breaks

Each failure below is manufactured from sim_class_returns_monthly, so that the message the reader will meet in practice is printed here first.

A ragged panel. Drop one row, the EU_equity observation for 2101-01-31, and cross the boundary.

ragged <- sim_class_returns_monthly[-5, ]

R_ragged <- withCallingHandlers(
  as_xts_pm(ragged, date, class, return),
  warning = function(w) { cat(conditionMessage(w), "\n"); invokeRestart("muffleWarning") }
)
#> Padded 1 missing return with "NA".
#> ℹ PortfolioAnalytics will not warn about these, but they change the effective
#>   sample of every moment estimate.
#> → Handle the gaps before crossing the boundary.

na_at <- which(is.na(R_ragged), arr.ind = TRUE)
c(row = as.character(zoo::index(R_ragged))[na_at[, "row"]],
  column = colnames(R_ragged)[na_at[, "col"]])
#>          row       column 
#> "2101-01-31"  "EU_equity"

The coercion pads rather than refuses, and says so. Two consequences follow. The first is that EU_equity has moved from column 5 to column 16, because as_xts_pm() orders columns by first appearance in the table and the dropped row was that asset’s first appearance. The second is what an optimizer does with the gap. For a variance objective, set.portfolio.moments() estimates the mean with na.rm = TRUE and the covariance with use = "pairwise.complete.obs", so one column is estimated on 371 months and the other fifteen on 372, and the matrix that results is the covariance of no sample that exists. The minimum-variance problem below is the one Section 9.2 builds up properly; here it only shows that the optimizer accepts the padded matrix without comment.

spec_of <- function(x) {
  portfolio.spec(assets = colnames(x)) |>
    add.constraint(type = "full_investment") |>
    add.constraint(type = "long_only") |>
    add.objective(type = "risk", name = "var")
}
w_full   <- extractWeights(optimize.portfolio(R,        spec_of(R),        optimize_method = "ROI"))
w_ragged <- extractWeights(optimize.portfolio(R_ragged, spec_of(R_ragged), optimize_method = "ROI"))

w_ragged <- w_ragged[names(w_full)]            # index by name: the columns moved
max_shift <- max(abs(w_ragged - w_full))
round(c(largest_weight_change = max_shift, cells_missing = sum(is.na(R_ragged))), 4)
#> largest_weight_change         cells_missing 
#>                0.0027                1.0000

The weights move by at most 0.0027, small because one month in 372 is small; the same gap in the sixty-month windows of Section 25.2 is one month in sixty, and a sleeve of instruments that list and delist, the setting of Section 21.1, is ragged by construction. The warning is the only notice the reader gets, and it comes from the coercion, not the optimizer. Handle the gap in the long table, before crossing.

Column order. The sort order of the long table becomes the column order of the matrix. Sort it differently, as a join or a dplyr::arrange() might, and the columns come out in a different order, from the same numbers.

reordered <- sim_class_returns_monthly |> dplyr::arrange(date, dplyr::desc(class))
R_rev     <- as_xts_pm(reordered, date, class, return)

c(same_set = setequal(colnames(R), colnames(R_rev)),
  same_order = identical(colnames(R), colnames(R_rev)))
#>   same_set same_order 
#>       TRUE      FALSE
colnames(R_rev)[1:3]
#> [1] "US_government" "US_equity"     "US_credit"

Now take a weight vector built in the original order, a 60/40 portfolio of US_equity and US_government, and apply it to the reordered matrix. Return.portfolio() pairs weights with columns by position.

w <- setNames(numeric(ncol(R)), colnames(R))
w[c("US_equity", "US_government")] <- c(0.6, 0.4)

rp <- merge(PerformanceAnalytics::Return.portfolio(R_rev, weights = w),
            PerformanceAnalytics::Return.portfolio(R_rev[, names(w)], weights = w))
colnames(rp) <- c("positional", "by_name")
PerformanceAnalytics::table.AnnualizedReturns(rp, Rf = rf)
#> # A tibble: 3 × 2
#>   positional by_name
#>        <dbl>   <dbl>
#> 1     0.0938   0.114
#> 2     0.150    0.130
#> 3     0.464    0.692

The positional column is a portfolio of CH_equity and CH_credit, because those are the series that now occupy the positions the weights were written for, and nothing reports that it is the wrong one. The guard is the condition of Equation 1.2, that the index of the weights and the index of the columns are the same index:

tryCatch(stopifnot(identical(colnames(R_rev), names(w))),
         error = function(e) cat("Error:", conditionMessage(e), "\n"))
#> Error: identical(colnames(R_rev), names(w)) is not TRUE

w <- w[colnames(R_rev)]                          # reindex by name, then assert
stopifnot(identical(colnames(R_rev), names(w)))

The same discipline applies coming out of the optimizer. extractWeights() returns a named vector in the column order of the matrix it was fitted on, and a vector fitted on one ordering and applied by position to another mis-pairs every entry.

Duplicate keys. If a date–asset pair appears twice, the table describes no matrix, and the failure surfaces in two steps.

dup <- dplyr::bind_rows(sim_class_returns_monthly,
                        dplyr::slice_head(sim_class_returns_monthly, n = 1))

tryCatch(
  withCallingHandlers(
    as_xts_pm(dup, date, class, return),
    warning = function(w) { cat("Warning:", conditionMessage(w), "\n"); invokeRestart("muffleWarning") }),
  error = function(e) cat("Error:", conditionMessage(e), "\n"))
#> Warning: Values from `return` are not uniquely identified; output will contain
#> list-cols.
#> • Use `values_fn = list` to suppress this warning.
#> • Use `values_fn = {summary_fun}` to summarise duplicates.
#> • Use the following dplyr code to identify duplicates.
#>   {data} |>
#>   dplyr::summarise(n = dplyr::n(), .by = c(date, class)) |>
#>   dplyr::filter(n > 1L) 
#> Error: cannot convert lists to xts objects

The warning comes from tidyr::pivot_wider() and names the cause; the error comes from xts() and names only the symptom, and a reader who sees the error alone has no way back to the duplicated pair. The check belongs before the crossing, in the long table, where the keys are columns:

dup |> dplyr::count(date, class) |> dplyr::filter(n > 1)
#> # A tibble: 1 × 3
#>   date       class         n
#>   <date>     <chr>     <int>
#> 1 2101-01-31 CH_credit     2
stopifnot(!anyDuplicated(sim_class_returns_monthly[c("date", "class")]))

These three chunks are the first appearance of a rule the book applies wherever two objects have to line up and nothing in the language enforces it: state the invariant as an assertion that fails the render, not as a comment. Index by name, then assert that the names agree. The rule recurs in Section 9.2, where weight vectors are indexed against the columns of the return matrix and group limits against the output of split(), and in Section 25.2, where a rolling optimization that fails in one window must not enter the record as a portfolio that did not move.

1.3 A First Pass Through the Data

1.3.1 How the code in this book is written

Every chapter opens with the same lines, run from the project root.

source("R/_common.R")                                              # seed, options, theme
library(tidypm)                                                    # the market, the boundary
R  <- as_xts_pm(sim_class_returns_monthly, date, class, return)   # sixteen risky classes
rf <- sim_riskfree_monthly$return                                  # the Treasury bill
Re <- R - rf                                                       # excess returns

R/_common.R attaches the tidyverse, xts and the two analytics packages, sets the seed to 1602, sets the printing options, registers theme_tidyaa() as the default ggplot2 theme with the palette tidyaa_colors and the scale scale_colour_tidyaa(), and warns if the installed PortfolioAnalytics is not the build the lockfile records (Appendix D). The data then load in two lines and a third subtracts the bill (Section 3.1); no chapter prepares data beyond this.

Three conventions follow. Every number in the prose is computed inline from an object a chunk created, never typed. Every figure is built from one long data frame, one row per plotted thing, so that an \(x\) cannot be paired with another row’s \(y\); that frame is usually the output of as_pm(). And ggplot2’s colour argument keeps its spelling in code while the prose is American. A reader who has not written R recently will find the language itself in Appendix E.

1.3.2 The shape of the data

The matrix built above is what Section 4.1 describes and every chapter after it consumes, so its dimensions are worth reading once.

p <- xts::periodicity(R)
c(months = nrow(R), assets = ncol(R),
  from = as.character(start(R)), to = as.character(end(R)), scale = p$scale)
#>       months       assets         from           to        scale 
#>        "372"         "16" "2101-01-31" "2131-12-31"    "monthly"

372 months of 16 series, from 2101-01 to 2131-12, 31 years on a monthly grid. A figure of three of them shows the reverse crossing in use: the matrix goes back to long form, a grouped mutate compounds each series, and the plot is drawn from that one frame.

  dplyr::group_by(asset) |>
  dplyr::mutate(growth = cumprod(1 + value)) |>
  dplyr::ungroup()

ggplot2::ggplot(growth, ggplot2::aes(date, growth, colour = asset)) +
  ggplot2::geom_line(linewidth = 0.7) +

Later chapters omit the call to theme_tidyaa(), which R/_common.R has already set. One dollar in US_equity at the start of the sample is 44.6 dollars at the end, against 4.0 in US_government and 4.1 in GLOBAL_commodity.

PerformanceAnalytics::table.AnnualizedReturns(R[, few], Rf = rf) |>
  kable(digits = 3)

The function annualizes the bill itself and prints the rate it used. The return in the first row is compounded and the Sharpe ratio divides the excess over the bill by the volatility; Section 4.1 fixes these conventions for the book and says where the arithmetic mean is used instead.

1.3.3 Reproducibility

Three things are pinned so that a reader’s numbers match the printed ones: the seed, set once in R/_common.R; the 299 package versions in renv.lock, with freeze: auto in _quarto.yml so that a chapter is re-executed only when its source changes; and the modeled market, at dataset version 6.2.0. The last pin is the one to respect most, because the source model redraws its idiosyncratic components on every run, so a regenerated dataset is a different realized path rather than a refresh; Section 2.2 explains why regenerating it is an event. The text is executed by knitr (Xie 2015) and assembled by Quarto (Allaire et al. 2022), the arrangement of the two books this one sits beside, Scheuch et al. (2023) and Coqueret and Guida (2020), and for the same reason: a number the reader cannot recompute is a number the reader cannot check.

Key Takeaways

  • Two data models are unavoidable. The tidy long table of Wickham (2014) is where a return panel is built, filtered and joined; the date-indexed matrix of Zeileis and Grothendieck (2005) and xts is what every function in PortfolioAnalytics and PerformanceAnalytics consumes, and it is the \(\boldsymbol{R}\) of
  • The boundary is crossed in a fixed direction, one call each way: as_xts_pm() from long to wide, once, after the panel is built; as_pm() from wide to long whenever a result is to be drawn.
  • The boundary fails in three ways, none reported downstream: a ragged panel is padded and each moment is then estimated on a different sample; a differently sorted table gives a differently ordered matrix, so weights applied by position land on the wrong assets; a duplicated key fails with an error that names only the symptom.
  • The guard is the same in every case: index by name, then assert that the names agree, with a stopifnot() that fails the render.
  • The _v1 and _v2 exports of PortfolioAnalytics are legacy shims; the book uses the unsuffixed functions. The package fetches no data and optimizes what it is given.
